# v3.2.1 配置库 SQL 导出与导入还原设计

- **日期**: 2026-10-02
- **状态**: 待审阅
- **前置**: v3.2 自备份(`data/selfbackup/` 快照 + API + 前端卡片)已上线。本批次扩展其格式与还原能力。

## 1. SQL 导出

- 新函数 `export_sql_dump(data_dir, keep=7, db=None)`:连接 `data/sqlite/app.db`,以 `conn.iterdump()` 生成纯文本 SQL(含建表与全部数据,自带 BEGIN/COMMIT),写为 `data/selfbackup/app-<YYYYMMDD-HHMMSS>.sql`;
- 保留策略:`.db.gz` 与 `.sql` 各自独立保留 7 份(轮转按名称时间戳排序);
- API:`POST /self-backup/run?fmt=sql|gz`(默认 gz,保持既有调用兼容);
- 列表与下载:白名单正则扩展为 `^app-\d{8}-\d{6}\.(db\.gz|sql)$`,列表项含类型字段(`kind: gz|sql`);
- 前端:自备份卡片新增"导出 SQL"按钮。

## 2. SQL 导入还原(重启生效)

- **两个入口**:① `POST /self-backup/import`(multipart 上传 .sql,≤20MB);② `POST /self-backup/{name}/restore`(列表内的 .sql);
- **校验**(两入口共用 `stage_restore(data_dir, sql_text)`):脚本先在临时空库执行 → 必须产出核心表(`accounts`、`db_connections`、`backup_records`、`schedules`、`notification_config`)→ 否则 400 拒绝(防垃圾/错误脚本在重启后变砖);
- **暂存**:校验通过 → 写 `data/sqlite/.restore-pending.sql` + 标记响应"重启容器后生效";
- **启动应用**(lifespan 之前,`create_app` 最早处调用 `maybe_restore(data_dir)`):检测暂存脚本 → 在临时库执行并复验核心表 → 当前 `app.db` 留底至 `selfbackup/pre-restore-<时间戳>.db`(防手滑回滚,保留最近 3 份)→ 清理旧 `-wal`/`-shm` → 原子 `os.replace` 新库 → 删暂存 → 返回还原信息;lifespan 初始化引擎后写 SystemLog(source=selfbackup)记录还原结果;
- **前端**:列表中 .sql 行加"还原"按钮(NPopconfirm 确认"重启容器后生效");卡片加"导入 SQL 还原"(上传文件)。

## 3. 不做(YAGNI)

二进制 `.db.gz` 的在线还原(上一轮已裁决不做)、SQL 编辑器内联预览、.sql 的定时自动导出、还原过程的差量合并(整库覆盖语义)。

## 4. 验证

- 单元:导出文件可被 sqlite 执行并还原数据;轮转独立计数;import 校验拒绝缺核心表的脚本;暂存→maybe_restore 全链路(留底生成/标记清理/核心表存在);下载白名单扩展;超限 413;
- E2E:建连接 → 导出 SQL → 删除该连接 → 导入该 SQL(staged)→ 重启容器 → 连接恢复、pre-restore 留底存在;/docs 与自备份回归;
- 全量:pytest、前端构建、docker build、CI 绿。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 恶意/错误 SQL 在重启时执行 | 暂存前临时库预执行 + 核心表校验;失败即拒绝且不影响运行中系统 |
| 还原覆盖手滑 | pre-restore 自动留底(保留 3 份) |
| iterdump 与自增序列 | dump 含 sqlite_sequence,重建后自增连续 |
| 大文件上传 | 20MB 上限(413),配置库远小于此 |
